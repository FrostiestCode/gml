Architecture

Two DLLs, one game import, and a rule that nothing may hard-code a game address. This page follows the boot path and explains why each piece is shaped the way it is.

Shape of the install

JustCause3.exe │ │ imports DirectInput8Create ├─ dinput8.dll GML.Loader │ forwards to the real dinput8, │ then loads the core │ └─ GrappleModLoader.dll GML.Core ├─ core/Runtime boot order and ownership ├─ core/GameVersion exe fingerprint ├─ core/SignatureDb signatures.json ├─ core/Hook inline / IAT / vtable / byte hooks ├─ core/Event event bus + DispatchGate ├─ core/Console command registry and scrollback ├─ core/InputBlock gameplay input gates ├─ core/Seh the single __try boundary ├─ core/Crash minidumps and reports ├─ overlay/ D3D11 Present hook, text renderer, panels ├─ game/ player, props, catalog, harvest, C ABI └─ mods/ModLoader discovery, order, init/shutdown, reload

The loader stays boring

Just Cause 3 imports exactly one function from dinput8.dll: DirectInput8Create. GML's proxy forwards that call to the real system DLL and loads GrappleModLoader.dll. It does nothing else.

That constraint is deliberate. The loader runs before any of GML exists, so it is the one component that cannot fail loudly or depend on configuration, signatures or the overlay. If the proxy is wrong, nothing else gets a chance to report why.

Boot order

The core runtime initialises in a fixed order:

  1. Detect the game version and fingerprint the exe.
  2. Resolve install paths and load config.json.
  3. Load signatures.json, scan patterns and verify bytes.
  4. Install the hooks the resolved signatures allow.
  5. Start the crash handler and input gates.
  6. Start runtime model harvesting and the tick thread.
  7. Discover and load mods in priority order.

Anything unresolved is skipped and logged. The rest of the loader still comes up, which is why the console remains useful even when a gameplay feature is unavailable.

Signatures, not addresses

signatures.json is the only place a game address may live, and even there the entry stores how to find the address rather than the address itself. Each entry carries a module, section, byte pattern, optional RIP-relative operand, dereference chain and verification bytes. The running exe's fingerprint must match the build the entry was researched against.

If the fingerprint does not match, the entry resolves to nothing and callers get GML_ERR_NOT_RESOLVED. The research page covers the status ladder and the rules for adding an entry.

Hooks

One registry owns every hook: inline trampolines, IAT slots, vtable slots and raw byte patches. Each hook records its owner (the mod id or a core subsystem), so unloading a mod can remove exactly its hooks without touching anyone else's.

Hooks are for observation and input, not for rewriting gameplay logic. Transforms are changed through data the engine already consults, which is why the teleport survives.

Event bus and the DispatchGate

Mods subscribe to string-named events: gml.tick, gml.present, gml.console.command, and so on. Dispatch copies the listener list and calls handlers outside the mutex, so a handler may emit another event without self-deadlocking.

The DispatchGate is a reader/writer gate between dispatch and module unloading. Emit enters as a reader. Unloading a DLL enters as the writer and waits until every in-flight callback has returned.

Before the gate existed, a reload on the window thread could FreeLibrary a mod while the render thread was still inside its Present listener. The game died in the unloaded DLL's frame. The gate is the fix, and it is why reload survives repeated hot-swaps.

A listener that requests a reload from inside a dispatch cannot take the writer lock without deadlocking against itself. That case is detected, logged, and unload runs ungated as a loud best effort.

The second rule from the same incident: subscribe with your mod id as the owner. A literal owner string leaks the subscription across reloads, and the dangling pointer faults every tick afterwards.

Input gating

JC3 reads gameplay input through two paths that bypass ordinary window messages:

  1. DirectInput GetDeviceState / GetDeviceData for the keyboard. GML inline-hooks the real device slots while a panel is open.
  2. USER32!GetCursorPos polling for mouse and camera. GML swaps the game's IAT slot and hands it a frozen cursor, so the game's self-computed deltas are zero.

Overlay panels also swallow keyboard and mouse messages in the subclassed WndProc, so menu keys never reach the game's own UI. This is why typing in the console does not move Rico and navigating the spawn menu does not spin the camera.

Overlay

The console hooks IDXGISwapChain::Present using a vtable address derived from a throwaway device. The first frame teaches it the game's device, context and window. Text is drawn through a GDI-rasterised glyph atlas: no font assets, no ImGui, and a much smaller auditable footprint. D3D11 state is fully saved and restored around the draw.

The spawn menu is a second panel drawn by the same renderer. Opening one closes the other — one panel owns the keyboard at a time.

One SEH boundary

Exactly one file contains __try. Everything else calls through seh::Guard, seh::Call or seh::CallVoid with POD hand-off records. Every game call that may fault — spawn, vtable setters, the harvest piggyback — is wrapped. A fault costs the feature, never the game.

Mods must not add their own __try; GML already wraps calls into mod code, and nested handlers change how frames unwind.

The game model

All JC3-specific knowledge lives in game/ as data plus validated pointer chains:

  • Player chain. The local player manager leads to the network player and then the character. Position and health read and write through this chain.
  • Teleport. The authoritative transform is the world matrix embedded in the interaction context reached from the character. Writing its translation row moves Rico and the engine keeps it. The obvious character transform is only engine output and gets reverted within a frame.
  • Spawn. The spawn-system singleton calls an async spawn function with a model name, a matrix and flags. The callback arrives later, so handles are recorded and reported by prop.status.
  • Harvest. Entity definition files carry a model-name property. A unique signature on the property getter is detoured at startup, and every streamed file contributes its name to the catalog.

Offset-based facts that are not signatures — embedded matrices, pointer-chain hops — live in Jc3Layout.h with per-constant provenance and are validated at runtime, not trusted. Exact addresses and evidence stay in the repository's RE write-up rather than being copied around the web.

Mods

A mod is a 64-bit DLL exporting GML_ModInit and optionally GML_ModShutdown, described by mod.json. Load order comes from priority; shutdown runs under SEH and anything forgotten is removed by owner. The ABI is pure C, versioned by leading size fields, with each side freeing its own memory. See Mod format.

Why it is shaped this way

  • Fail visibly. Missing signatures are logged and surfaced as a result code, not papered over.
  • Small trusted core. The proxy is trivial; the risky game calls are isolated and SEH-wrapped.
  • Data-driven addresses. A new build means new signatures, not a new binary full of hard-coded offsets.
  • Unload is a feature. Hooks, events and commands are owner-tracked so hot reload is real.
  • No UI framework. The overlay stays a text renderer, which keeps the dependency surface and the frame cost down.
