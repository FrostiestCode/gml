Signatures & research

No address ships without a signature, and no signature is trusted unless it matches this exe build and byte-verifies at load. This is how GML keeps game addresses honest across builds.

Why signatures

Function addresses move between builds, and hard-coded addresses are how mods crash other people's games. GML therefore resolves everything at load time from a build-keyed signature database, and refuses to use an entry researched against a different build. The installed exe is one specific build — SizeOfImage 0x3241000, TimeDateStamp 0x5787641C (SHA-256 recorded in MODDING_PLAN.md).

Each entry stores how to find an address — module, section, byte pattern, optional RIP-relative operand, dereference chain and verification bytes — not the address itself. Resolution runs once at boot; if the running exe's fingerprint does not match the entry's build key, the entry resolves to nothing and callers get GML_ERR_NOT_RESOLVED.

Schema

{
  "name": "SpawnSystem::Spawn",     // unique key; code asks for it by name
  "kind": "function",               // function | pointer | rip | read | ...
  "access": "call",                 // call | read | readPointer | rip | none
  "module": "",                     // "" = the main exe
  "section": ".text",               // where the pattern is scanned
  "pattern": "48 8B C4 57 ...",    // IDA-style bytes; ?? = wildcard
  "rip": null,                      // {operandOffset, instructionSize} when the pattern
                                    //   lands on a rip-relative reference to the target
  "deref": [],                      // follow-up pointer reads, if any
  "object": "", "objectOffset": 0,  // for instance-based entries
  "verify": "48 8B C4 57 ...",      // bytes that must exist at the resolved address
  "build": { "imageSize": 52695040, "timestamp": 1468490780 },
  "status": "verified",             // verified | experimental | unresolved
  "source": "static analysis 2026-10-19: ...",
  "note": "what this is and the evidence"
}

Resolution (core/SignatureDb.cpp): scan the section for the pattern (it must be unique), apply RIP extraction if present, follow the dereference chain, then check the verification bytes. The entry's source and note fields record where the pattern came from and why it exists — there are no anonymous offsets.

Status ladder

StatusMeaningWhat it lets you do
Unresolved No entry yet, or the pattern is not recorded. Any feature that needs it reports GML_ERR_NOT_RESOLVED and names the entry. The honest default.
Experimental The pattern resolves and the verify bytes match, but behaviour has not been shown working in game. Treat with care; call it, but do not ship a feature on it yet.
Verified Resolved and demonstrated on this build. Upgrading requires evidence — a log line, a spawn handle, a teleport that sticks — not just a successful scan.

Rules for adding an entry

  1. Find it in the real binary. Use tools/gml_re.py (cached disassembly sweep plus xrefs), tools/jc3_vfind.py for RTTI vtable reverse lookup, or tools/rtti_full.py for the class map. Never type an address from a forum post into code — at most into signatures.json with a source that says where it came from.
  2. Derive the pattern from the function's real entry bytes. Wildcards only for bytes that genuinely vary (RIP-relative operands). Prove uniqueness across the whole .text.
  3. Record verify bytes — the first stable instruction bytes — so a bad load is detected at load time, not suffered later.
  4. Write source and note as evidence, including addresses from this build.
  5. Prove it in game before flipping status to verified, and keep the log line as the receipt.

JC3 API provenance

GML's player, vehicle, entity and world blueprint comes from jc3-api (MIT, © 2016 Alexander Guettler): object layouts, the map of what functions matter, and the vtable calling convention. Nothing from that project is trusted as an address — its targets belong to a different build than the installed JustCause3.exe. GML takes the model and proves every address itself against this exe. The build-mismatch proof and full research write-ups live in the repository:

  • JC3_API_REFERENCE.md — jc3-api inventory and why its addresses cannot be used as-is.
  • RE_PLAYER_CHAIN.md — player chain, teleport, spawn, harvest evidence.
  • GETMODELHASH_RESEARCH.md — how the model hash was solved.
  • MODDING_PLAN.md — original recon and the recorded build fingerprint.

jc3-console-thingy (MIT, © aaronkirkham) was cross-checked for the model-harvest mechanism. The source docs and exact signature patterns stay in the repository; this page describes the system, not a dump of offsets.
